## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| 路径级绕过 | **不存在**。闸门与路由用同一个 `new URL().pathname`，闸门只会多拦不会漏拦（大小写、`//`、`./`、`%2F`、尾随斜杠两边都不命中） |

| 配额体系 | **可绕过**：两个高危端点的配额键由客户端决定（S4、S5）；计数无 CAS，并发可放大额度（S7） |
| 管理面 | 鉴权实现正确（常量时间比较、缺 token 时 fail-closed），风险在**令牌泄漏后的破坏半径**（S9） |

#### S1 浏览器豁免可伪造（P0）

```js
// 4675
function licBrowserAllowed(request, env) {
  if (!request.headers.get('sec-fetch-mode')) return false
  const raw = request.headers.get('origin') || request.headers.get('referer') || ''
  ...
  return list.some((allowed) => host === allowed || host.endsWith('.' + allowed))
}
```

`Sec-Fetch-*` 系列对**浏览器脚本**是禁止修改头，对 `curl`、`HttpClient`、任何自研客户端只是普通 header。因此：

```
POST /api/oss-sign
Origin: https://classsoftwarehub.cn
Sec-Fetch-Mode: cors
Content-Type: application/json
```

在 `licEnforce=true` 之后依然直接放行。**影响**：开闸后投稿、上传签名、喊话三个付费点仍可白嫖，授权体系实际不成立。

**修复方向**（按成本从低到高）：

1. 网页端改为先调 `/api/license/browser-issue` 换一枚短时令牌（服务端校验 `Sec-Fetch-Site: same-origin` + `Referer`，并在页面上放一个不可见的服务端下发 nonce），后续请求复用令牌 —— 与桌面端走同一条令牌通道，删掉整个豁免分支；
2. 若暂不改造，至少要求 `Sec-Fetch-Site: same-origin` + `Sec-Fetch-Mode: cors` + `Referer` 三者同时命中，并把 `endsWith('.' + allowed)` 改成精确 host 集合（当前允许任意子域）。

#### S2 旧客户端豁免（P1）

`4694`：`CSH_LIC_LEGACY_UNTIL` 非空且未到期时，**完全不带 `X-CSH-Build`** 的请求直接放行。当前默认空（未启用），但 README 的上线建议里曾把它与开闸并列，容易误配。一旦启用，任何人不带这个头即可绕过闸门。

修复：豁免条件改为「不带 `X-CSH-Build` **且** `X-CSH-Ver` 在允许的旧版本集合内」，集合由后台参数维护；或直接删除该分支，旧版本强制升级。

#### S3 官方构建可换出通用令牌（P1）

`4736` 用请求头设备码签发令牌，设备码可为空；`4640` 的校验对空 `d` 短路：

```js
if (payload.d && payload.d !== device) return null   // d="" 时不校验
```

而构建签名 `HMAC(secret, "v1|" + buildId)` 是静态字符串，可从任意官方安装包的程序集元数据里提取。两者叠加：**提取一次签名 → 换出 30 天通用令牌 → 全网分发**，且该令牌不绑定设备、不受封禁影响（无设备码时 `licBanInfo` 直接跳过）。

修复：

```js
// licIssueToken 入口
if (!deviceIdOk(String(device || ''))) return null   // 无设备码不签发
```

同时把构建签名加时间维度（`v1|<buildId>|<yyyy-mm>`，客户端按月轮换签名），使静态提取的签名在一个月后自动失效。

#### S4 投稿配额可关闭（P0）

```js
// 1138
async function submitterIdOf(data) {
  const raw = String((data && (data._设备 || data.fp)) || '').trim()
  if (raw.length < 8 || raw.length > 256) return ''      // 长度不符 → 空
  return (await sha256Hex(raw)).slice(0, 16)
}
// 1205
if (!sid) return { ok: true }                            // 空 → 直接放行
```

请求体里删掉 `_设备` 与 `fp`，即可同时跳过每日次数与待审条数两项限制，无限投稿 → 无限建 Issue。

修复：`sid` 为空时回落到服务端派生值（`sha256(reqIp + UA)`），与 `dl-ticket` 同源逻辑；至少不应 `return { ok: true }`。

#### S5 下载每日限额可轮换绕过（P0）

```js
// 2400（注释写着「配额键必须由服务端派生」，实现并非如此）
const device = deviceIdOf(request)                    // 来自客户端头
const ua = String(request.headers.get('user-agent') || '').slice(0, 128)
const fp = device || `ip:${clientIpOf(request)}|ua:${ua}`
```

`deviceIdOf` 只校验格式（16–64 hex），值仍由客户端任意指定。每次请求换一个随机 hex，或删掉设备头后改 UA，就是新的配额桶。25 次/天形同虚设。

修复：配额键与票据绑定的 `fp` 分离——配额只用 `clientIpOf(request)`（边缘写入，不可伪造，需实测确认，见 §3），票据仍用客户端 `fp`。另外 `/api/dl` 取流前应复查配额与封禁（当前只验签，票据 15 分钟内可无限次取流）。

#### S6 激活码无消费语义（P1）

`licRecordActivation`（`4249`）只累加 `hit.n`，从不拒绝。同一码可在任意设备上重复兑换。是否算漏洞取决于产品预期：若主打「一码一机」，需在兑换时判断 `hit.u` 是否已被其他设备占用；若允许一码多机（如班级授权），应在文档里明说，避免售后纠纷。

#### S7 配额计数无 CAS（P1）

`submit-tick`（`3578`）、`gateSignCheck`、`repCheck`（`4419`）、`bytes-add` 全部是「读整表 → 改一个数 → 整表写回」。Blob 无 compare-and-swap，并发请求各自读到同一个旧值，最终只 +1。

两个后果：
1. 配额可被并发放大（N 并发 ≈ N 倍额度）；
2. `file-put` 并发丢登记记录 → 已上传对象被判「未登记」，投稿被 400 拒绝，或被 GC 当孤儿删掉（数据丢失）。

修复：计数改为「一次事件一个 key」（`gate:q:<bucket>:<minute>:<rand>` + 列举汇总），或按前 2 位哈希分片；登记表拆成 `f:<key>` 单对象，索引只存 key 列表。

#### S8 `DL_SIGN_SECRET` 缺失即空密钥（P1，需查控制台）

```js
// 2029
const secret = textEncoder.encode(String(env.DL_SIGN_SECRET || ''))
```

`handleDlTicket` 只检查中继/OSS 是否配置，不检查签名密钥。密钥为空时算法全在开源代码里，可自行算出 `k/e/h/s` 直接调 `/api/dl` 取流，绕过票据、配额与登记校验。

修复：`handleDlTicket` 与 `handleDl` 开头加 fail-closed 判断；`/api/status` 增加 `dlSign: boolean` 便于巡检（当前只暴露 `buildSecret` / `licenseSecret`）。

**已被审计员排除的方向**（避免重复投入）：

- **路径归一化绕过**：`licenseGuard` 与 `routeRequest` 用同一个 `pathname` 与同样的比较方式，斜杠/编码变体在两边都不命中路由，不构成绕过。
- **OSS key 注入**：`ossSafeName` 先按 `/`、`\` 截断再过滤控制字符与 `..`，无法逃出前缀目录。
- **SSRF / 开放跳转**：`mirror-sign` 用 `URL.hostname` 精确匹配，`github.com.evil.com`、`user@host`、`127.0.0.1` 全部不通过；`icon`、`dl`、`relay` 的目标 host 全部来自环境变量。
- **CORS 白名单**：`getOrigin` 是 `list.includes(origin)` 精确匹配，不是 `endsWith`，子域伪造不成立（但 `licBrowserAllowed` 里的 `endsWith` 成立，见 S1）。
- **常量时间比较**：`ctEqual` 与 `licSameBytes` 在等长分支上逐字节 XOR，无提前返回，实现正确。
- **`ENV_DEFAULTS` 残留密钥**：已核查，只有域名/桶名/开关，无任何真实密钥。

## 2. 性能

### 2.1 端点成本

`registryOp` 在 EdgeOne 上是「进程内 dispatch + 1~2 次 Blob 往返」，下表统一按 Blob 往返计。典型请求 = 带设备码的桌面客户端。

| 端点 | 同步往返 | 后台往返 | 外部请求 | 主要瓶颈 |
|---|---|---|---|---|
| `POST /api/dl-ticket` | **14** | 3~4 + GC 摊销 | 1 次中继 HEAD | 同 key 两次 `file-get`、`stats` 两读、`cfg` 两读、ban 重复读 |
| `GET /api/dl` | **0**（带设备码 1 次 ban） | 1 | 1 次上游 | 纯流式转发，无存储开销 |
| `POST /api/submit` | **15**（2 个上传项，每多 1 项 +3） | 0 | 3~4 GitHub + N 次 HEAD | 每次查整张登记表、GitHub search |
| `POST /api/oss-sign` | **9** | 4（登记写 4 次） | 0 | `file-put` 写两张表、两次 presign 共 10 次 HMAC |
| `POST /api/echocave` / `feedback` | **8** | 0~1 | 1 GitHub | ban 重复读 + 信誉计数 |
| `GET /api/announce/poll` | **7** | 1 | 0 | 每轮整表读改写设备绑定表 |
| `POST /api/announce/send` | **10~11** | 0 | 0 | `gateAnn` 内 5 次串行写 |
| `GET /api/status` | **7** | 0 | 2~3 | 全桶列举、心跳写后回读、无缓存 |

按 20–40ms/次往返估算，`dl-ticket` 的 14 次 ≈ **300–560ms 纯等待**，还没算中继探测。

### 2.2 主要问题

| 编号 | 类型 | 位置 | 现象 |
|---|---|---|---|
| P1 | 存储模型 | `90`、`3442` | 登记表是单 blob（上限 1000 条 ≈ 200KB）：查 1 个 key 要下载并 `JSON.parse` 整表；写 1 条要整表覆写 4 次往返。1000 条之后 `file-map` 直接 `break`，GC 看不到第 1001 条起的孤儿 |
| P2 | 浪费往返 | `2421`+`2464` | `dl-ticket` 对同一个 key 查两次 `file-get`；`stats` 两读（且 `DL_RELAY_MONTHLY_GB` 默认 `0` 时结果恒为 false，纯浪费）；`cfg` 两次读；ban 三次读（`4453`/`4720`/`2407`） |
| P3 | 阻塞首字节 | `5785` | GC 懒触发在**进入路由之前** `await kvJson(KV_CFG)`，每个 `dl-ticket` 无条件 +1 往返；节流用读改写，边缘多实例下等于「每实例 20 分钟」 |
| P4 | 热 key | `3667` | `announce/poll` 每轮都整表读改写（无论是否变化）：60 台设备 10 秒轮询 ≈ 360 次写/分钟打同一个 blob，并发还会互相覆盖导致设备「消失」 |
| P5 | 串行 await | `1626`、`1654`、`3171`、`3233` | 投稿按下载项串行 `registryHas` + `relayOpen(HEAD)`；GC 逐条删；四前缀列举串行 |
| P6 | 缓存失效 | `1085` vs `5775` | `settingsOf` 的 15 秒 memo 挂在 `env` 上，而每请求都 `Object.assign` 新建 `env` → 跨请求 100% miss，每请求固定多 1 次读 |
| P7 | GitHub 成本 | `1144`、`1208` | 每次投稿打一次 `search/issues`（认证后 30 次/分钟）；`submit-tick` 在文件校验与 GitHub 写入**之前**计数，失败不回滚，重试 N 次吃 N 次日配额 |
| P8 | 无超时 | 全文件 | `relayOpen`、`relayProbe`、`mirror-sign`、`knownPlatformKeys` 全裸 `fetch`，无 `AbortSignal`；中继黑洞时表现为「下载卡住」 |
| P9 | 重复计算 | `174`、`1336` | 每次 `hmacSha256` 重新 `importKey`；`oss-sign` 两次 presign 共 10 次 HMAC，其中 8 次 KDF 可复用 |
| P10 | 图标整读 | `3828` | MISS 时把最大 5MB 整体 `arrayBuffer()` 只为嗅探前 12 字节（有 7 天边缘缓存，命中时无成本） |

**正面结论**：`/api/dl` 用 `new Response(relay.body, ...)` 直接透传，不落内存；`Range` / `206` / `Content-Range` 均正确透传；`HEAD` 正确释放读锁。下载主链路没有内存与流式问题。

### 2.3 优化清单（按收益/成本排序）

| 优先级 | 位置 | 现在 | 优化后 | 做法 |
|---|---|---|---|---|
| 优 1 | `2421`+`2464`+`2470`+`2469`+`2407` | 14 次往返 | **9 次（−36%）** | 复用第一次 `file-get` 的结果当 `rec`；`relayCap > 0` 才查 stats；`dlModeWanted` 接受已读到的 cfg；ban 结果从 `deviceGuard` 透传给闸门 |
| 优 2 | `5785` | 每个 dl-ticket +1 读，触发时 +1 写 | 首字节 −1 往返，GC 不阻塞 | `lastGc` 拆独立 key，读取放进 `waitUntil`；或移到响应之后 |
| 优 3 | `3442`、`3505` | 每次查/写全表（200KB@1000 条） | 单 key O(1) | 登记拆 `f:<key>` 单对象 + 索引仅存 key 列表（或按前 2 位分 256 片） |
| 优 4 | `3676` | 每 poll 写整表 | 写降 ~95% | 只在「新设备」或 `t` 距今 >60s 时写；设备条目独立键 |
| 优 5 | `3180` | 孤儿 >100 整轮放弃 | 积压可排空 | 改为每轮处理前 100 个并返回 `remaining`；删除改并发 3 |
| 优 6 | `1626`、`1654` | 每项 3 次串行 | 省 ~2/3 等待 | `Promise.all` + 并发闸（HEAD 3 / Blob 5） |
| 优 7 | `1085` | 每请求 1 次 settings 读 | −1 往返 | memo 挂 `globalThis`（带 `at` 时间戳），或 env 克隆提到模块级 |
| 优 8 | `1208`、`1144` | 每投稿 1 次 search，失败不回滚 | search 降一个量级 | `submit-tick` 移到 GitHub 写入成功之后；`countPendingIssues` 按 sid 加 60 秒负缓存 |
| 优 9 | `5637` | 7 往返 + 全桶 + 2 外网，每 30 秒 | 命中缓存 0 往返 | `caches.default` 缓存 JSON 60 秒；心跳写改 `waitUntil` 且不回读；删掉匿名 `rate_limit` 探测 |

## 4. 建议的修复顺序

**第一批（开闸前必须做，12-02 之前）**

1. S1 浏览器豁免改造 —— 不改等于闸门形同虚设；
