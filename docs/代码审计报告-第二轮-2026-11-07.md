### 2.1 【安全·未修】提权助手从用户可写目录读删除清单 → 管理员级任意删除

**位置**：`src\Services\LeftoverCleaner.cs:672`、`:691-696`、`:781-787`、`:894-929`

清单落在 `%LOCALAPPDATA%\ClassSoftwareHub\quarantine\<任意名>\admin-tasks.json`。助手只校验「在隔离区内 + 文件名对」（`:781-787`），而 `ValidateManifestEntry` 对路径类条目只要求**绝对路径 + 不在禁碰名单**（`:911-917`）：

```csharp
// LeftoverCleaner.cs:911-917
if (e.Kind == (int)FootprintKind.Path)
{
    if (!Path.IsPathRooted(e.Path)) { reason = "相对路径"; return false; }
    if (LeftoverResolver.IsForbiddenPathPublic(e.Path)) { reason = "路径受保护"; return false; }
    return true;
}
```

**禁碰名单不保护"其他用户的数据"**：`C:\Users\张三\Documents`、`D:\学校资料` 全部通过校验并被 `Directory.Delete(recursive:true)`。

**触发链**：同用户低权进程写入恶意清单 → 用户点一次 UAC（"残留清理"）→ 管理员级递归删除任意非系统目录。`FileShare.None` 只在写入瞬间有效，**UAC 弹窗期间那份文件是自由可写的**。

**判定**：旧报告 P0 #8 的窗口**只是被缩小，并未消除**。

**修法方向**：助手不再信任低权进程写出的清单 —— 改用 DPAPI 机器密钥 + 附加熵对清单做 HMAC，或改「命名管道传参 + 助手侧重算候选」。

### 2.3 【逻辑·修错】一价离子 `H^+` / `OH^-` 一律被拒 → **所有离子方程式都无法配平**

**位置**：`src\Services\ChemistryBalancer.cs:353-374`（`StripCharge`）

```csharp

{
    var charge = formula[(caret + 1)..^1];
    if (charge.Length > 0 && charge.All(char.IsDigit))   // ← 一价时 charge == ""
    {
        formula = formula[..caret].TrimEnd();
        chargeIgnored = true;
        return true;
    }
    error = $"「{raw}」的电荷写法看不懂，请写成 Fe^3+ 或 SO4^2- 的形式。";
    return false;
}
```

`^` 与 `+`/`-` 之间没有数字时（`H^+`、`OH^-`、`Na^+`、`Cl^-`），`charge` 是空串，`charge.Length > 0` 为假 → **直接报错**。

**我的独立实测**（`.tmp\lead-probe`，链接生产源码）：

```
输入: H^+ + OH^- = H2O            → Ok=False  Err=「H^+」的电荷写法看不懂…
输入: H⁺ + OH⁻ = H2O              → Ok=False  Err=「H⁺」的电荷写法看不懂…
输入: Cr2O7^2- + Fe^2+ + H^+ = …  → Ok=False  Err=「H^+」的电荷写法看不懂…
输入: MnO4^- + Fe^2+ + H^+ = …    → Ok=False  Err=「MnO4^-」的电荷写法看不懂…
输入: NO3^- + H^+ = NO + H2O      → Ok=False  Err=「NO3^-」的电荷写法看不懂…
输入: SO4^2- + Ba^2+ = BaSO4      → Ok=True   （多价正常）
输入: Fe + O2 = Fe2O3             → Ok=True   Eq=4Fe + 3O2 = 2Fe2O3
```

**讽刺之处**：提示语自己举的例子 `Fe^3+` 能过，但提示语要解决的**一价离子**过不了；用户照着提示改也改不出来 —— 他没有任何写法能表示 `H^+`。而高中化学的离子方程式、离子共存、电极反应**全部**是 1 价离子参与的。

`src\Services\ChemicalFavorites.cs:25-29` 把下面 8 个离子写死为编辑器「常用离子根」面板的默认按钮：


### 2.5 【逻辑·修错】大根漏解：`x²=10¹⁰` 只给 1 个根

**位置**：`src\Services\EquationSolver.cs:387`（`for (var i = 1; i <= steps; i++)`）+ `:437-448`（固定扫描窗）

`Scan` 采样时 `i=0` 被求值存进 `ys[0]`（`:366-375`），但主循环**从 `i=1` 起**（这一步本身**是对的**，因为需要 `ys[i-1]`），于是 `ys[0]` 只作为 `prevY` 参与变号判断，**永远不会被 `if (y == 0) Push(x)` 检查到**；而偶重根分支又要求 `i >= 2`，左端点也进不去。而最后一窗 `Scan(-100_000, 100_000, 120_000)` 的左端点 `-100000` 恰好就是 `x²=1e10` 的负根（`f(-100000)` 精确为 0）。

**我的独立实测**：

```
x^2 = 10000000000  → 1 个解: x = 100000          ← 应为 ±100000
x^2 = 10000000001  → 0 个解（报"没有找到实根"）  ← 应为 ±100000.000005
x^2 = 9999999999   → 2 个解: x = ±99999.999995    ← 正确（根在窗口内部）
x^2 = 1e12         → 0 个解                        ← 应为 ±1000000
f(-100000) = 0（精确为 0，就是被跳过的那个点）
```

**"越整越错"最阴**：老师举 `x²=10¹⁰` 这种整数例子（最常见的课堂例子）恰好必踩。而界面提示「已按方程本身的性质求根，**与窗口大小无关**」—— **这句话是假的**，根能否被找到完全取决于 `Scan` 的三个固定窗口。

**判定**：旧报告的 P0-2（绝对阈值 1e-6）修复确实解决了"判无实根"，但**没解决"漏解"** —— 从"0 个根"变成"1 个根"，仍然错。

### 2.13 【逻辑·实测】`Validate` / `Solve` 被 `FormatException` / `OverflowException` 打穿 → **边输边校验会白屏**

**位置**：`src\Services\LinearForm.cs:183`（`int.Parse`），两个 catch 只认 `LinearParseException`

```csharp
// LinearForm.cs:177-183
_i++;
var start = _i;
SkipSpace();
while (_i < _s.Length && char.IsDigit(_s[_i])) _i++;
if (start == _i) throw new LinearParseException("指数写法有误。");

var exponent = int.Parse(_s[start.._i]);   // ← start.._i 可能不是纯数字 / 超长
```

**我的独立实测**：

```
Validate(x ^ a = 4)                  -> ❌ FormatException
Validate(x ^ (2) = 4)                -> ❌ FormatException
Validate(x^999999999999999999999 = 4)-> ❌ OverflowException
Validate(x^2147483648 = 4)           -> ❌ OverflowException
Validate(x^2 = 4)                    -> ok=True（正常）
Validate(x ^ 2 = 4)                  -> ok=True（正常）
```

**为什么是 P0 而不是 P2**：`Validate` 是**边输入边调用**的（决定"确定"按钮能否点，见 `EquationSolver.cs:36-43` 的注释）。用户在方程页输入 `x ^ ` 后继续敲字母，就会走到 `int.Parse("")` 或非数字串 → **未捕获异常直接冒到 UI 线程** → 白屏 / 崩溃。这不是"要特意构造"，是**打字过程中的自然路径**。

**附带同类**：`x^0 = 1` 返回 `x = 0`，而正确结果是**恒等式（全体实数）**。`LinearForm.cs:185-190` 对未知数的 0 次方是抛错而不是当 1 —— 语义选择的后果是另一处错误结论。

## 6. 三重防线为何全失效（这是"屎山"的根）

### 6.1 编译器/分析器：把 65 条债压成「0 警告」

```
src\ClassSoftwareHub.Win7.csproj:68   <NoWarn>$(NoWarn);CA1416</NoWarn>
Directory.Build.props:15              <EnableNETAnalyzers>false</EnableNETAnalyzers>
Directory.Build.props:16              <EnforceCodeStyleInBuild>false</EnforceCodeStyleInBuild>
Directory.Build.props:14              <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
```

**实测**（`dotnet build -t:Rebuild -p:NoWarn="" -m:1`，权威输出 `65 个警告 / 0 个错误`）：

| 警告码 | 条数 | 性质 |
|---|---:|---|
| AVLN3001 | 27 | 窗口缺 public 构造函数 → **运行时 loader 必崩** |
| CS0618 | 19 | 过时 API（`ToggleButton.Checked` 等） |
| **CS8602** | **15** | **可能空引用解引用 → 会崩 UI** |
| CS0114 | 2 | `Show()` 隐藏继承成员 |
| CS8600 | 1 | 可空转换 |
| CS8604 | 1 | 可能 null 参数 |
| **合计** | **65** | 日志里 130 行是每条报两遍（并行构建重复），去重后 65 |

> 注：并行构建（不带 `-m:1`）在本机会触发 `AVLN9999 System.OutOfMemoryException` 构建失败 —— 那是**本机环境问题**，非源码缺陷；`-m:1` 单进程 0 错误通过。

**分析器全开**（`-p:AnalysisLevel=latest-all`，干净 OutputPath）= **3751 条**。而 `Directory.Build.props:6-8` 的注释写「178 条」—— **低估 20 倍**（那是默认 AnalysisLevel 的数量）。

**更关键**：CA1416（平台兼容性分析器）**即便强行开启也一条都不报**。原因：仓库用自定义 `[DllImport]` 声明 Win32 API，分析器无从得知其最低系统版本。所以 **Win7 兼容性 100% 靠手写 try/catch 和人工记忆**，没有任何自动化兜底 —— 这正是 `GetWindowLongPtr`（§2.8）这类错误能长期存活的土壤。

### 6.2 测试：14/14 PASS 是虚假信心

```csharp
// tests\ClassSoftwareHub.SelfCheck\Program.cs:53-59
var bigRoot = EquationSolver.Solve("x^2 = 10000000000");
Check("大根 x^2 = 1e10 不应判无实根", bigRoot.Solutions.Count > 0, ...);  // ← 只查 >0
```

`x²=1e10` 只返回 **1** 个根（应为 2 个），断言 `Count > 0` **完美掩盖**了漏解（§2.5）。

```csharp
// Program.cs:40
var safe = !r.Ok || normalized.Contains(token, StringComparison.Ordinal);
```

**只要报错就算通过** → 化学一价离子全部报错（§2.3）时这条断言依然 PASS，掩盖了"该成功却失败"。

`SelfCheck` 工程本身是好的（零 NuGet、`<Compile Include>` 链接 8 个真实源文件、14 条断言真跑），但**断言设计只防"输出被截肢"，不防"该算对却算错"**。

### 6.3 布局：`Services` 直接 `using Avalonia`，分层只是目录名

`Services\` 148 文件 / 41,463 行（31.6%）占近 1/3，但**没有接口层、没有模块边界**，且大量直接引用 Avalonia UI 类型（`ThemeBrush.cs`、`TeachingActions.cs`）。UI 层 45,975 行零测试覆盖。
