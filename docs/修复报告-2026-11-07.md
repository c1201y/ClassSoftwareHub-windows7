## 2. 关键修复详解

### 2.1 化学：一价离子 + 电荷守恒（P0-3 / P0-4）

**根因**：`StripCharge` 里 `if (charge.Length > 0 && charge.All(char.IsDigit))` —— 一价离子在 `^` 与 `+/-` 之间**没有数字**，`charge` 是空串，条件为假 → 直接报错。

**改动**：
- `StripCharge` 改为输出实际电荷数 `out int charge, out bool hasCharge`，新增「`^` 后无数字 ⇒ 按 ±1 处理」分支。
- `ParseFormula` 三参数改五参数，把电荷透传出来。
- `Balance` 在有电荷时**给消元矩阵多加一行「电荷守恒」**，并对结果做电荷核对；不平就 `Fail`。
- `Result` 新增 `ChargeCheck` 字段；`ChemistryPage` 的核对表**并列显示「电荷」一行**（+2 / -1 / 0 带符号）。

**实测**：
```
出厂预置 8 个离子根：8/8 通过（修前 3/8）
Cr2O7^2- + 6Fe^2+ + 14H^+ = 2Cr^3+ + 6Fe^3+ + 7H2O   电荷 24/24 ✅
MnO4^- + 5Fe^2+ + 8H^+ = Mn^2+ + 5Fe^3+ + 4H2O       电荷 17/17 ✅
Fe^2+ = Fe^3+   → 拒绝（电荷不平）✅
Fe + O2 = Fe2O3 → 4Fe + 3O2 = 2Fe2O3（回归正常）✅
```

### 2.2 方程：大根漏解（P0-5）

**根因**：`Scan` 采样时 `i=0` 的值存进 `ys[0]`，但主循环**从 `i=1` 起**（这一步本身正确，需要 `ys[i-1]`），于是 `ys[0]` 永远只作为 `prevY` 参与变号判断，**从不被 `if (y == 0)` 检查**；偶重根分支又要求 `i >= 2`。而 `x²=1e10` 的负根 `-100000` 恰好就是最后一窗 `Scan(-100000,100000)` 的左端点。

**改动**：
1. 补 `if (ys[0] == 0) Push(from);` —— 单独判一次左端点。
2. 扫描窗从 `±1e5` 扩到 `±1e6`（覆盖 `x²=1e12`）。
3. `FormatRoot` 的整数判定改用**相对容差** `1e-11×|v|`，既能识别 `999999.999999996 → 1000000`，又不会把 `99999.999995` 抹成 `100000`。
4. 文案修正：删掉「与窗口大小无关」这句假话，改为「已扫描 ±1e6」。

**实测**：
```
x^2 = 10000000000  → x = −100000 | x = 100000        （修前只有 1 个）
x^2 = 1e12         → x = −1000000 | x = 1000000      （修前 0 个）
x^2 = 1e10         → x = −100000 | x = 100000
```

### 2.3 方程：科学计数法（P0-6）

**根因**：`ParsePrimary` 读数字时只吃 `char.IsDigit` 和 `.`，读到 `1` 就停；后面的 `e10` 被当**变量名**。于是 `x = 1e10` 变成「x 与 e10 两个未知数」→ 答"无穷多组解"。

**改动**：数字读取后**探测 `e`/`E`**，若后面确实跟指数数字就整体吃掉；否则回退（保持 `2e` 仍是「2×变量e」的原语义）。`FromDecimal` 同步改为字符串拼 `BigInteger`，不再走 `decimal.ToInt64`（大数会溢出）。

**实测**：`x = 1e10 → x = 10000000000` / `x = 2E-3 → x = 1/500` / `x + 1e2 = 300 → x = 200`。

### 2.4 方程：异常打穿（P0-13）

**根因**：`LinearForm.cs:183` 的 `int.Parse(_s[start.._i])`，且 `start` 在 `SkipSpace()` **之前**取（`x ^ 2` 会截出 `" 2"`）→ `FormatException`；超长指数 → `OverflowException`。而 `Solve`/`Validate` 的 catch 只认 `LinearParseException`，异常直穿到 UI 线程（`Validate` 是边输边调的）。

**改动**：
1. `start` 移到 `SkipSpace()` **之后**。
2. `int.Parse` → `int.TryParse`。
3. `Solve` / `Validate` 各补一个 `catch (Exception)` 兜底。

**实测**：`x ^ a = 4`、`x ^ (2) = 4`、`x^999999999999999999999 = 4` 全部不再抛异常。
**附带**：`x^0 = 1` 现在正确报「x = 任意实数」（修前显示 `x = 0`）。

### 2.5 绘图：陡直线消失（P0-7）

**根因**：渐近线判据 `(y > 0) != (prevY > 0)` —— `y=2000x` 在视口内只占 `x∈[-0.15,0.15]`，其余采样点全在视口外且跨 0，被整体判为渐近线 → **整条曲线消失**。

**改动**：改用**中点加密采样**判据（唯一可靠的判法）：
```csharp
var midX = prevX + (x - prevX) * 0.5;
var midY = EvalSafe(f, midX);
var linear = (prevY + y) * 0.5;
if (!double.IsFinite(midY) || Math.Abs(midY - linear) > jumpSize * 0.25)
    ok = false;   // 真的不连续
```
连续函数（含陡直线）的中点必然贴近线性插值；`1/x`、`tan` 跨极点时中点会偏离极远。

**实测**：
```
y = 2000x / 5000x / 10000x / 50000x → 均 1 段 800 点（修前 0 段）
1/x → 2 段  |  tan(x) → 7 段  |  1/x^2 → 2 段   （不连续仍正确断开）
x^2 / sin(x) / exp(x) → 1 段 800 点
```

### 2.6 平台：32 位 `GetWindowLongPtr`（P0-8）

**根因**：`EntryPoint = "GetWindowLongPtr"` 无 W 后缀也无位宽路由。实测 32 位 `SysWOW64\user32.dll` **零个 `*Ptr*` 导出**。

**改动**：拆成两组 extern + 按 `IntPtr.Size` 路由的包装方法（公开签名不变，调用点无需改动）：
- 64 位 → `GetWindowLongPtrW` / `SetWindowLongPtrW`
- 32 位 → `GetWindowLongW` / `SetWindowLongW`（`int` ↔ `IntPtr` 转换）

### 2.7 AI：孤儿 tool 消息（P0，会话每问必 400）

**根因**：旧实现边遍历边把已配对的 tool 消息 `Add` 进 `rebuilt`，发现这组没答全时只 `RemoveAt(ownerIndex)` 摘掉 assistant —— **已加进去的 tool 留在结果里**，成为「前面没有 `tool_calls` 的 tool 消息」，服务端照样 400。

**改动**：改为**暂存列表法** —— 一组 tool 消息先存 `pendingTools`，组关闭且**答全**时才整体 `AddRange` 进 `rebuilt`；没答全就整组丢弃，不再需要算下标位移。

**结构性保证**：唯一往 `rebuilt` 放 tool 消息的分支就是「答全」那一支，所以「孤儿 tool」在结构上不可能出现。

**顺带修掉反方向破损**：原方法开头有 `if (_messages.All(m => m.Role != "tool")) return;` —— 这行让函数对
「assistant 带 `tool_calls`、后面一条 tool 都没有」的破损历史视而不见（同样会被服务端 400），
而它自己的 XML 注释却写着「反之亦然」。已删除并注明原因。`dropped == 0` 早退仍保留，所以
无变化时不会重写消息列表。

**验证**：抽出方法体注入独立 .NET 6 工程 —— 7 个手写场景（半应答整组消失、有正文时正文保留、
答全组原样保留、天然孤儿、连续两组一全一半、反向破损、无关历史不变）+ **20000 例随机 fuzz**，
每次同时断言两个不变式（无孤儿 tool；每个 assistant 的 tool_calls 都有应答或已被摘除）→ 全过。

### 2.8 AI：SSE `finish_reason`（P0）

**根因**：全仓搜索 `finish_reason` **零命中**。`max_tokens` 截断时服务端照样发 `[DONE]`，客户端把半截结论当完整回答。

**改动**：
1. `ChunkMeta` 新增 `FinishReason` 字段；`AccumulateChunk` 解析 `choices[0].finish_reason`。
   ⚠️ 必须从原返回 `AiUsage?` 改成新的 `readonly struct ChunkMeta { Usage?, FinishReason? }` ——
   usage 与 finish_reason 常出现在**不同块**（usage 在 `choices: []` 的尾块，finish_reason 在最后一块正常 delta 上），
   一个返回槽位装不下两样。
2. 流结束后若 `finish_reason == "length"` → 正文末尾追加 `TruncatedNotice` 可识别提示并 `AppLog.Warn`。
   **有工具调用时不追加**（截断点很可能正切在 arguments 的 JSON 中间，塞提示只会更乱）。
3. **多行 `data:`** 改为按标准 SSE 语义（空行才是事件边界）缓冲拼接。
   附加一条兜底 `LooksLikeCompleteJson`：有的服务商**单行 data 且不发空行**，纯「只认空行」
   会把两条 JSON 粘成一条、两块正文一起丢（修一个 bug 又造一个新的）。
4. **UTF-8 BOM** 首行 `TrimStart('\uFEFF')`（只剥首行；正文中间的 BOM 是内容，不能动）。
5. **额外修的洞**：`[DONE]` 现在**立刻结算并跳出**，不再等空行 —— 服务商发完 `[DONE]` 不一定关连接，
   旧逻辑会继续 read 直到 120 秒空闲超时，把一次成功的回答变成 `TimeoutException`。
   EOF 断流前也先 `DispatchEvent()` 一次，避免丢掉没有空行收尾的最后一块。

**验证**：9 个用例（正常流、BOM 首块、多行 data 拼接、**不发空行的服务商不能退化**、
length 追加提示、工具截断不追加、tool_calls 收尾、未结算事件不丢、usage 兼容）→ 全过。

### 2.9 UI：`ShowWebSheet` 的 try（P1）
